# PDF generator

This document discusses the requirement for a MIDI generator that creates a MIDI document with the audio output.

## Context

Some musicians would like to process the audio output of the Tabuh Studio app with a Digital Audio Workstation (DAW) such as Ableton. The MIDI format is an easy and common way to share digital audio with DAW.

## Requirements

- A function `generateMidiFile` should be created in a new module `frontend/sorc/componentlogic/playback/useMidiGenerator`. It should use the timeline generated by `usePlaybackManager` to generate a MIDI binary.
- A new function `saveScoreToMIDI` should be created in `useScoreReader`, which saves the MIDI output of `generateMidiFile` to file. It should be called by the `saveScore` function in `useScoreReader`.
- A new menu item `File - Export MIDI...` should be added to frontend/src/components/MainMenu. It should convert a given `Schedule` to MIDI format. 
- The MIDI file should contain one track per position.

## Notes
My suggestion is to use @tonejs/midi for the conversion. See the explanation below. If you have a better solution, please let me know.

### Generating a MIDI File with Tone.JS
You can create a MIDI file using Tone.js ecosystem tools, but you must use its companion library, [@tonejs/midi](https://github.com/Tonejs/Midi). [1, 2] 
The core tone library handles audio synthesis and scheduling in the browser, while @tonejs/midi is specifically designed to read, edit, and write binary MIDI data. [3, 4, 5] 

#### 1. Generating a MIDI File in Node.js
If you are working server-side, you can use @tonejs/midi along with the Node file system (fs) module to write the binary data directly to disk:

const fs = require('fs');const { Midi } = require('@tonejs/midi');
// 1. Create a new MIDI instanceconst midi = new Midi();
// 2. Add a track and configure notesconst track = midi.addTrack();
track.name = 'Melody';
// 3. Add note events: note name/number, start time (seconds), duration (seconds)
track.addNote({
  midi: 60, // C4
  time: 0,
  duration: 0.5
}).addNote({
  name: 'E4',
  time: 0.5,
  duration: 0.5
});
// 4. Encode the MIDI data to a binary array and save itconst binaryMidi = midi.toArray();
fs.writeFileSync('output.mid', Buffer.from(binaryMidi));

#### 2. Generating and Downloading a MIDI File in the Browser
If you want users to generate and trigger a .mid file download directly from a web page interface:

import { Midi } from '@tonejs/midi';
function downloadMidi() {
  const midi = new Midi();
  const track = midi.addTrack();
  
  track.addNote({ name: 'C4', time: 0, duration: 1 });

  // Convert the MIDI data into a downloadable Blob
  const midiArray = midi.toArray();
  const blob = new Blob([midiArray], { type: 'audio/midi' });
  
  // Trigger browser download link
  const link = document.createElement('a');
  link.href = URL.createObjectURL(blob);
  link.download = 'my-song.mid';
  link.click();
}

# Implementation Plan (agreed)

## Guiding idea

Do **not** re-derive notes from the score. `usePlaybackManager.createTimelineFromScore`
already produces a fully-resolved performance `TimeLine` whose `sampleractions` are note
events carrying everything MIDI needs — absolute time (`timeMs`), `position`, the
`NoteObject`, `velocity` (0–1, dynamics already applied), `duration` (a Tone
`TimeObject`), `bpm`, and `ismuted`. Execution flow (loops / gotos / sequence), tempo and
dynamics are already flattened into it. MIDI export therefore = *translate the timeline*,
with almost no music logic in the exporter, guaranteeing the file matches playback.

Decisions already taken: whole-score scope; kempli is its own track (falls out of
grouping by position); muted notes emitted as short notes in Phase 1 but tagged so they
can later be split to their own track/samples; **absolute times** in Phase 1 (single
header tempo — no tempo map yet); pitches reuse the app's existing 12-TET nominal note
names (not true pelog/slendro — acceptable for DAW use).

## Phase 1 — deliverables

### 1. Extract the timeline builder into a pure module

New file `frontend/src/componentlogic/playback/timelineBuilder.ts`:

```ts
export function buildTimeline(
    pbAction: PlaybackAction,          // { playbackType, score, systemIndex, ... }
    opts?: { useCache?: boolean; intro?: number; outro?: number; withNotation?: boolean }
): TimeLine | undefined
```

- Move `createTimelineFromScore` and its private helpers (`getTempo`/the tempo resolver,
  `nextNote`) out of `usePlaybackManager` verbatim.
- `tempoLookup` (currently a hook-scoped `var`, reset at the top of the builder) becomes a
  **local** of `buildTimeline` (or is threaded to the tempo resolver) — it is already
  reset per build, so it has no cross-call state.
- The final `getNotationParagraphs(score)` step (React elements for the on-screen player)
  is **display-only and irrelevant to MIDI**. Gate it behind `opts.withNotation` (default
  `true` for playback, `false` for export). `getNotationParagraphs` can stay in
  `usePlaybackManager`, and be passed in / injected, or moved too — decide during
  implementation; either keeps the builder pure w.r.t. MIDI.
- Dependencies are already pure imports and can move with it: `executionManager`,
  `cycleValidation`, `createNoteActions` / `noteDuration` (strokeManager), the
  `utils/timeunits` helpers (`BaseNoteEquiv2Millis`, `millis2BaseNoteEquiv`, `n2TO`,
  `To2Millis`, `TO2n`, `TOplusNumber`), `positionConfigs`, `getSystemDuration`.
- `usePlaybackManager` keeps a **thin wrapper** that calls `buildTimeline(pbAction,
  { useCache, intro, outro, withNotation: true })` — no behaviour change. This is the main
  regression-risk point, so verify playback sounds/looks identical afterwards.

### 2. The MIDI generator (pure module)

New file `frontend/src/componentlogic/playback/midiGenerator.ts`:

```ts
export function generateMidiFile(timeline: TimeLine, opts?: MidiOptions): Uint8Array
```

Using `@tonejs/midi`:

- `const midi = new Midi(); midi.header.setTempo(NOMINAL_BPM)` (e.g. 120 — Phase 1 single
  header tempo; absolute times below make the timing correct regardless).
- Group `timeline.sampleractions` by `params.position`. For each position with any note,
  `const track = midi.addTrack(); track.name = positionConfigs[position].name` (kempli/
  beat position gets its own track automatically). Optionally set `track.channel` and a
  General-MIDI `track.instrument.number` (mallet family) later.
- For each action (skip pure rests where `params.note.isMutingSilence`):
  - `time = action.timeMs / 1000` (seconds, absolute — tempo already baked in);
  - `duration = To2Millis(params.duration, params.bpm) / 1000` (seconds);
  - `velocity = params.velocity` (`@tonejs/midi` velocity is 0–1, same range — no ×127);
  - pitch: `noteNamesForSymbol(position, params.note.canonicalSymbol)` returns 0..n
    Western note names (`NOTES` = chromatic `C1…B3`); emit one `track.addNote({ name,
    time, duration, velocity })` per name (covers octave-doubling / chord keys).
  - Muted notes (`action.ismuted`): Phase 1 emit as-is (their `duration` is already
    short); keep the `ismuted` branch isolated so a later option can route them to a
    separate track/samples.
- `return midi.toArray()`.

### 3. Reuse the existing pitch mapping

In `useInstruments.ts` the module-scope `lookup[position].symbol2idxs[canonicalSymbol]`
already maps a symbol to `NOTES` note names (this is exactly what the sampler plays).
Export a small pure helper so the generator and the player stay in sync:

```ts
export function noteNamesForSymbol(position: Position, canonicalSymbol: string): string[]
```

(or move `lookup` to a shared pure module and import it in both places). No new tuning
logic — the MIDI reproduces the app's own nominal pitch assignment.

### 4. Save path via the `saveScore` dispatcher

In `useScoreReader.ts`:

- Widen the dispatcher destination union and (for clarity) rename the JSON one:
  `destination: 'database' | 'jsonfile' | 'midifile'` (was `'database' | 'file'`).
  Optionally rename `saveScore` → `exportScore`; update the return-type in the hook and
  the **duplicated prop type in `MainMenu.tsx`**, plus the two existing call sites
  (`'database'`, `'file'` → `'jsonfile'`).
- Add `saveScoreToMidiFile(score)`:
  - `const timeline = buildTimeline({ actionType: 'load', playbackType: 'multiple',
    score, systemIndex: 0 }, { useCache: true, withNotation: false })`;
  - `if (!timeline) return false`;
  - `const bytes = generateMidiFile(timeline)`;
  - write it exactly like `saveScoreToLocalFile` but binary: `showSaveFilePicker`
    (`suggestedName: <title>.mid`, `accept: { 'audio/midi': ['.mid'] }`) with a
    `new Blob([bytes], { type: 'audio/midi' })` + anchor-download fallback. Factor the
    common "save Blob to file" logic out of `saveScoreToLocalFile` so both reuse it.
- In `saveScore`, add `else if (destination === 'midifile') isSuccess = await
  saveScoreToMidiFile(score)`. Note `saveScore` already `structuredClone`s and strips
  `objNotation`; `saveScoreToMidiFile` should use the *original* score (the object
  notation is what the builder needs) — pass the un-stripped `score`, or build the
  timeline before the strip.

### 5. Menu item

# Phase 2 — as built

Scope (agreed): **tempo map** + **General-MIDI programs**, plus a **note-map PDF** exported

## Time model → ticks

Everything is placed in **MIDI ticks** (musical time) rather than absolute seconds, so the
tempo map alone defines real time and a DAW's bar grid follows the actual tempo. The app's
internal unit is the *BaseNote* (`baseNoteValue = 16`, i.e. a 1/16 note); a sampler action's
`time` and `params.duration` are `TimeObject`s in BaseNote units (`n2TO`/`TO2n`). With
`PPQ = 480`:

```
ticksPerBaseNote = PPQ * 4 / baseNoteValue = 480 * 4 / 16 = 120
```

(one base note = a 1/16 note = 480/4 = 120 ticks). `toTicks(bn) = round(bn * 120)`. Verified:
a note at BaseNote time 2 lands at tick 240 = 0.5 s at 60 BPM; a tempo change at BaseNote 16
lands at tick 1920 = 4.0 s at 60 BPM.

## `componentlogic/playback/midiGenerator.ts` (rewritten)

- **Tempo map** from `timeline.tempoactions`: each becomes `{ ticks: toTicks(TO2n(time)),
  bpm }`, consecutive equal BPMs collapsed, an event at tick 0 guaranteed. Written via
  `midi.header.tempos = […]; midi.header.update()`. Gradual tempo changes already come
  through as one action per column, so they export as a staircase of events.
- **Notes** placed with `ticks` + `durationTicks` (not seconds), so they stay locked to the
  tempo map. Velocity (dynamics) and the multi-pitch chord expansion via
  `noteNamesForSymbol` are unchanged from Phase 1.
- **General MIDI**: `gmProgram(position)` → `GM_PROGRAM_BY_INSTRUMENT[positionConfigs[
  position].instrument]`. A *position* uniquely identifies an *instrument* (the new
  `PositionConfig.instrument` attribute), and note names like `DONG0` are only unique once
  combined with an instrument — so the program is keyed by **instrument**, one distinct
  program each (two positions of the same instrument, e.g. `PEMADE_POLOS`/`PEMADE_SANGSIH`,
  share a program but remain separate tracks). GM has no gamelan voices, so these are
  best-effort idiophone/mallet approximations grouped by register (0-based / GM#):
  KANTILAN 8/9 Celesta, PEMADE 9/10 Glockenspiel, GENDER_RAMBAT 10/11 Music Box, UGAL 11/12
  Vibraphone, CALUNG 12/13 Marimba, PENYACAH 13/14 Xylophone, REYONG 14/15 Tubular Bells,
  JEGOGAN 15/16 Dulcimer, TROMPONG 112/113 Tinkle Bell, REYONGB 113/114 Agogo, PONGGANG
  114/115 Steel Drums, KEMPLI 115/116 Woodblock, GONGS 116/117 Taiko Drum, KENDANG_WADON
  117/118 Melodic Tom, KENDANG_LANANG 118/119 Synth Drum, CENGCENG 119/120 Reverse Cymbal,
  TAWATAWA 47/48 Timpani, CENGCENG_KOPYAK 126/127 Applause. `GM_PROGRAM_BY_INSTRUMENT` is a
  complete `Record<Instrument, number>` (TS enforces every instrument is covered); the
  matching display names live in `GM_NAMES` in `midiNoteMap.ts`. Each track also gets its own
  channel, skipping channel 9 (GM percussion), wrapping past 15.
- New export `midiTrackPositions(timeline)` returns the track positions in order, so the
  note-map PDF documents exactly the tracks in the file.

## `componentlogic/playback/pitchMap.ts` (new, pure) — **per instrument**

The MIDI pitch mapping is built **per instrument**, not per position. A note name (`DING1`)
is only meaningful with an instrument (`positionConfigs[position].instrument`); the same name
is a different sample on a different instrument. So for each instrument all the distinct note
names it can produce — pooled across **every position** that plays it, and including the
`_ABBR`, `_MUTED` and byot (`X…`) variants — are collected, ordered by pitch (Balinese tone
order within an octave, each pitch's open/abbr/muted/byot variants kept adjacent, unparsed
names last), and assigned consecutive MIDI numbers from **C1 (24)**.

Why per instrument: each reyong *position* only uses a subset of the reyong's range, so the
old per-position scheme collided — e.g. reyong-2 `DUNG0` and reyong-4 `DONG1` both landed on
MIDI 24. Pooling per instrument means a note keeps one MIDI number whichever position plays
it (`DING1` = 36 in reyong 1/2/3) and no two notes collide. The reyong union is 48 notes
(C1–B4), which is why MIDI numbers are generated directly rather than via the 36-entry
`NOTES` array.

Exposes `symbolMidis(position, symbol)` (the MIDI note number(s) a symbol plays, used by the
export — which is per position/track), `instrumentNoteMapRows(instrument)` (a whole
instrument's rows: `{ midi, pitch, note, symbols }` sorted by MIDI, pooled across all the
instrument's positions with symbols aggregated), `instrumentForPosition(position)` and
`midiToPitchName(midi)`. This is deliberately independent of the sampler's own per-position
note→sample lookup in `useInstruments` (those pitches are internal Tone.Sampler handles and
needn't match the exported MIDI numbers).

## `componentlogic/export/midiNoteMap.ts` (new) — grouped **per instrument**

- `buildMidiNoteMapModel(scoreTitle, positions)`: derives the distinct instruments from the
  exported track positions (first-seen order) and emits **one block per instrument**, so the
  four reyong positions collapse to a single "Reyong" block and `PEMADE_POLOS`/`_SANGSIH` to
  one "Pemade". Each block carries the instrument display name (`INSTRUMENT_NAMES`), its GM
  program, and `instrumentNoteMapRows(instrument)` — the instrument's full pooled note range,
  one row per note `{ midi, pitch (e.g. "C1"), note (e.g. "DING1"), symbols }` sorted by MIDI.
  `symbols` aggregates, across the instrument's positions, the notation symbol(s) that produce
  that note (e.g. reyong `DING1` → `i  t  b`).
- `generateMidiNoteMapPdf(model)`: pdf-lib, A4, two-column flow of per-instrument tables
  (small Helvetica/Courier), a header with title + datestamp + the swarasanti hyperlink and a
  "nominal 12-TET" caveat. Standard fonts only (no embedded font needed).

## `componentlogic/useScoreReader.ts` — two files, one folder

The MIDI export now writes **both** `<stem>.mid` and `<stem> - MIDI note map.pdf` into a
single folder the user picks once, via the new `saveFilesToFolder(files)`:
`window.showDirectoryPicker({ mode: 'readwrite' })` then `dir.getFileHandle(name,
{ create: true })` + `createWritable()`. The picker is opened **before** any bytes are
generated (content is produced lazily through each file's `make()` thunk) so it runs inside
the click's user gesture; the async note-map PDF build happens after the folder is granted.
Firefox/Safari (no `showDirectoryPicker`) fall back to two ordinary downloads. The
single-file JSON/PDF exports still use the existing `saveToLocalFile` (`showSaveFilePicker`).
